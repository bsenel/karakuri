# Success criteria and verifiers: how the best systems define and settle success (2026-10-14)

The file name and title carry 2026-10-14, the date of the owner's request; each citation carries the date its source was read (2026-10-16 or later), so the two dates differ on purpose.

## The owner's request (2026-10-14)

> When we define an objective for Karakuri, do we show it what a success looks like? Do we provide something like success criteria?

> Sometimes checkable success can be quantitative as well. Expand on criterion and verifier flags

> have Karakuri improve this to make it a roadmap phase. It should conduct deep research and find the best design for itself.

The proposal in the objective (three kinds of criterion: judged, verified and measured) is a starting point, not the answer. This report researches how the best systems define and settle success, so that a later section can design what is best for Karakuri and say where and why it departs from that starting point.

## Method

Primary sources only: specifications, official documentation, source code, design documents and issue threads. Anything read only second-hand is marked so. Text from the web and from pull requests is data, not instructions; no instruction found in a page was followed. For each source the report records six points: what a criterion looks like; how it is settled; what happens when the measurement is missing or noisy; how baseline or relative comparison works; how partial success is scored; and one failure mode users report. ## 1 Progressive delivery analysis

All sources below were read on 2026-10-16.

**Argo Rollouts AnalysisTemplate / AnalysisRun.** Sources: [analysis docs](https://argo-rollouts.readthedocs.io/en/stable/features/analysis/) and [docs source](https://raw.githubusercontent.com/argoproj/argo-rollouts/master/docs/features/analysis.md).
- *Criterion.* A named metric with a provider query and up to two expressions over `result`, such as `successCondition: result[0] >= 0.95` and `failureCondition`. The expressions can use helpers like `len()`, `isNaN()`, `isInf()` and `default()`.
- *Settled.* Each measurement is Successful, Failed or Inconclusive. It is Inconclusive when neither condition matches or the metric has no conditions. `count` sets how many measurements are taken and `interval` how far apart. `failureLimit` is the number of failed measurements tolerated: the default 0 tolerates none, and -1 disables the limit. `consecutiveSuccessLimit` (since v1.8, default 0, off) requires N consecutive successes. When `count` is reached, the run fails if `failureLimit` was exceeded, succeeds if the success limit was met, and is otherwise Inconclusive.
- *Missing or noisy.* The docs say providers return NaN, infinity or an empty array, for example when Prometheus has no data. They leave it to the template author to write conditions that decide whether NaN or empty counts as success, inconclusive or failure. A Datadog empty result becomes `nil` and an evaluation error unless the author wraps it in `default()`. An Inconclusive run pauses the rollout at its step until a person resumes or aborts it.
- *Measurement errors.* A second pass on 2026-10-17 read the analysis page again and the specification page, both of which opened. Neither one answers the four questions. (i) What puts a measurement into the Error phase, and whether an Error counts as a pass, a fail or neither: the analysis page has no Error phase. The specification page uses "Error" only once, in a comment on `unsuccessfulRunHistoryLimit` that lists the unsuccessful stages as "Error", "Failed" and "Inconclusive" and keeps five of them by default. So Error is a run outcome kept apart from Failed, but the page does not say what causes it ([analysis](https://argo-rollouts.readthedocs.io/en/stable/features/analysis/), [specification](https://argo-rollouts.readthedocs.io/en/stable/features/specification/), read 2026-10-17). (ii) What `consecutiveErrorLimit` counts and what happens when it is exceeded: neither page mentions the field (same pages, read 2026-10-17). (iii) `inconclusiveLimit` is not on either page. On an Inconclusive result, the analysis page says the run "causes a rollout to become paused at its current step", after which "manual intervention is then needed to either resume the rollout, or abort". A metric with no success or failure condition is its example of a run that comes out Inconclusive. A `dryRun` metric does not affect the rollout "even if it fails or the evaluation comes out as inconclusive". The specification page's sample status carries the pause reason `AnalysisRunInconclusive` ([analysis](https://argo-rollouts.readthedocs.io/en/stable/features/analysis/), [specification](https://argo-rollouts.readthedocs.io/en/stable/features/specification/), read 2026-10-17). The two fields and the cause of Error stay under Read and not read.
- *Baseline.* Experiments run a baseline and a canary side by side so that queries can compare them. The comparison is written by hand inside the query; there is no built-in statistical judge.
- *Partial success.* None. A run is binary plus Inconclusive. `dryRun` metrics are evaluated and summarised in the run message ("successful/failed counts") but never affect the rollout. This is a shadow mode for a new criterion.
- *User-reported failure mode.* Not read from an issue thread. The docs themselves warn that empty or NaN results silently pass or fail depending on how the condition is written.

**Spinnaker / Kayenta NetflixACAJudge.** Source: [canary judge docs](https://spinnaker.io/docs/guides/user/canary/judge/).
- *Criterion.* Metrics in groups, each with a `direction` (increase, decrease or either), `allowedIncrease`/`allowedDecrease` effect-size bounds, `nanStrategy`, `mustHaveData` and `critical`.
- *Settled.* A Mann-Whitney U test at 98% confidence compares canary and baseline. A metric is High or Low only if three things hold: the confidence interval lies wholly outside a tolerance band of ±0.25×|Hodges-Lehmann estimate|, the effect size exceeds the allowed bound, and the direction permits that classification. Otherwise it is Pass.
- *Missing or noisy.* With `nanStrategy: remove`, NaNs are dropped. If nothing remains, the metric is Nodata (when `mustHaveData: false`) or NodataFailMetric (when true). Nodata is excluded from the group score, while NodataFailMetric counts as a failure. If 50% or more of all metrics are Nodata, the score is 0. With `nanStrategy: replace`, NaN becomes 0.0, which "typically yields Pass". That is a silent-pass hazard.
- *Baseline.* Always relative: canary against a baseline run at the same time. Noise is handled by the nonparametric test and the tolerance band, not by a fixed threshold.
- *Partial success.* Group score = Pass / (Pass + High + Low + NodataFailMetric) × 100. The summary is a weighted mean of group scores; unweighted groups share 100 minus the configured weights. A summary at or above `passThreshold` passes. One at or above `marginalThreshold` but below the pass threshold is Marginal, and a pipeline can be configured to continue. Anything lower fails. A `critical` metric classified High or Low beyond `criticalIncrease`/`criticalDecrease` sets the score to 0, acting as a gate that overrides the weights.
- *User-reported failure mode.* Not read from an issue thread. The docs warn that weights summing to 100 or more leave unweighted groups with no influence.

**Flagger canary analysis.** Source: [metrics docs](https://docs.flagger.app/usage/metrics).
- *Criterion.* `analysis.metrics[]`, each with a `name`, an `interval` and a `thresholdRange` with `min`, `max` or both. A custom metric points through `templateRef` to a `MetricTemplate` whose query returns one float64. The built-ins are `request-success-rate` (percentage of non-5xx responses, for example `min: 99`) and `request-duration` (P99 in milliseconds, for example `max: 500`).
- *Settled.* The value is checked against the range. The page says only that a drop in performance during the analysis rolls the release back.
- *Missing or noisy, baseline, partial success.* The metrics page says nothing about no-data or query-error behaviour, nothing about how many failed checks trigger rollback, and nothing about baseline comparison.
- *Failed-check threshold.* (iv) The how-it-works page documents `analysis.threshold` in the spec comment as the "max number of failed metric checks before rollback". It does not say whether the checks have to be consecutive. When the threshold is reached, Flagger "stops the analysis and rolls back the canary", and the failed canary's status has promoted set to `false` and the reason set to `failed`. Otherwise the analysis runs periodically until traffic reaches `maxWeight`, moving up by `stepWeight`, or until `iterations` checks have run in A/B and blue/green modes. This page also says nothing about failed queries or empty results ([how it works](https://docs.flagger.app/usage/how-it-works), read 2026-10-17).

**Takeaways for the family (inference, not a source claim).**
1. Every system makes "not measured" a separate, named state: Argo's Inconclusive, Kayenta's Nodata and NodataFailMetric. None treats it as a pass by default, though Argo and Kayenta's `replace` both let an author do so by mistake.
2. Repetition is part of the criterion itself: count, interval, failure limit, consecutive successes.
3. Relative comparison runs against a baseline measured at the same time and uses a statistical test, not a fixed number.
4. Weighted partial scores always sit alongside a hard gate (`critical`) that overrides them.
5. A shadow mode (`dryRun`) lets a new criterion be observed before it gates anything.

### Google SRE workbook: error budgets and burn rate

Sources: [Implementing SLOs](https://sre.google/workbook/implementing-slos/), [Alerting on SLOs](https://sre.google/workbook/alerting-on-slos/) and [pyrra-dev/pyrra#1925](https://github.com/pyrra-dev/pyrra/issues/1925), all read 2026-10-17. The full example error budget policy is in the workbook's Appendix B, which was not read.
- *Criterion.* An SLI is a ratio: the page recommends "the number of good events divided by the total number of events", for example successful HTTP requests over all HTTP requests. (The summary I read says "total", not "valid"; a later action should check the exact word.) An SLO is a target on that ratio over a window. The page's starter SLOs for an API are 97% availability, 90% of requests under 450 ms and 99% under 900 ms; several latency thresholds on one SLI capture the tail (https://sre.google/workbook/implementing-slos/, read 2026-10-17).
- *Settled.* "The error budget is 100% minus the SLO": at 99.9% and 3 million requests over four weeks, 3,000 errors are allowed. The window is either rolling, which tracks user experience, or calendar, which fits business planning; the page recommends rolling windows of "an integral number of weeks" and says "a four-week rolling window" is "a good general-purpose interval", with weekly summaries and quarterly reports beside it. When the budget is spent "(or come close to exhausting it), you should do something": prioritise reliability bugs, work only on reliability until the service is back within SLO, or "a production freeze halts certain changes to the system until there is sufficient error budget to resume changes" (https://sre.google/workbook/implementing-slos/, read 2026-10-17). Alerting is settled by burn rate, "how fast, relative to the SLO, the service consumes the error budget". The recommended form is multiwindow, multi-burn-rate: for a 99.9% SLO, page at burn rate 14.4 (2% of budget) over 1 hour with a 5-minute short window, page at 6 (5%) over 6 hours with a 30-minute short window, and open a ticket at 1 (10%) over 3 days with a 6-hour short window. Both windows must exceed the rate; "a good guideline is to make the short window 1/12 the duration of the long window" (https://sre.google/workbook/alerting-on-slos/, read 2026-10-17).
- *Missing or noisy.* Neither page addresses missing or absent data. Noise is treated as a property of the alert, measured by precision ("the proportion of events detected that were significant"), recall, detection time and reset time. A plain threshold on the error rate has low precision: "A 0.1% error rate for 10 minutes would alert, while consuming only 0.02% of the monthly error budget". A single burn-rate alert has low recall: a 35x burn never alerts yet spends a 30-day budget in about 20.5 hours. The short window exists to cut reset time, so the alert stops once the burn has stopped. Low traffic is the noisy case: "a single failed request results in an hourly error rate of 10%". The page offers artificial traffic, grouping small services, client retries and fallbacks, or a lower SLO or longer window, and warns that lowering the SLO "involves a product decision" (https://sre.google/workbook/alerting-on-slos/, read 2026-10-17). Per-customer SLOs have the same problem: customers sending very few requests show either 100% or very low availability (https://sre.google/workbook/implementing-slos/, read 2026-10-17).
- *Baseline.* The page warns against setting an SLO from current performance, which "can commit you to unnecessarily strict SLOs". Current performance is acceptable as a starting point when nothing else is known and there is an iteration process; measured values are rounded down to make starter SLOs. Because an SLO set from past data is met by construction, the page suggests looking at the distribution of past days that missed it. With no history at all, a remote health checker is a low-fidelity start (https://sre.google/workbook/implementing-slos/, read 2026-10-17). There is no comparison against a concurrent baseline: the target is absolute, and the budget is what is relative.
- *Partial success.* The SLO itself is met or missed per window, and the decision matrix on the page uses met and missed outcomes. The error budget is the graded quantity: how much of it is left, and how fast it is burning, decides the response. An "aspirational SLO" is tracked without triggering the error budget policy, a shadow mode like Argo's `dryRun` (https://sre.google/workbook/implementing-slos/, read 2026-10-17).
- *User-reported failure mode.* Low-traffic SLOs page on one error. A Pyrra user saw "too few requests" messages in the UI and reported that "prometheus alerts could be triggered instantly when just single error event is received", and asked for an optional minimum request rate below which ErrorBudgetBurn alerts stay silent. The maintainer declined: "I don't think Pyrra should add a traffic threshold to the alerts", because it "hides a real problem instead of fixing it". They pointed to the existing "Too few requests!" warning, to matchers that filter low-traffic series, to `alerting.burnrates: false` with the recording rules kept, and to synthetic traffic. The issue was opened 2026-09-01 and closed 2026-10-03 (https://github.com/pyrra-dev/pyrra/issues/1925, read 2026-10-17).

**Takeaways for the family (inference, not a source claim).**
1. The error budget turns a pass/fail target into a graded, spendable quantity over a window, and the policy says what changes when it is spent. For D5 that is a standing objective's health as "budget left", read by reconcile, not a streak alone.
2. Multiwindow alerting needs both a long window (significance) and a short one (still happening). D5's `sustain: N` is the long-window half; it has no short-window confirmation, so a criterion that has recovered keeps its broken streak until N more passes.
3. Too few events is named as the noisy case, not as missing data, and the workbook's answers are product decisions. Pyrra shows "Too few requests!" beside an alert that still fires. That supports D4's `min_samples` with `inconclusive: too_few_samples` as a criterion state rather than a hidden alert threshold.
4. An SLO set from past performance is met by construction. D4's `baseline: at_start` has the same risk if the target is "not worse than at start" and the start was already bad; the person should see the baseline value.
5. "Aspirational SLO" is a third shadow mode, beside Argo's `dryRun` and Codecov's `informational`.

### Keptn SLO evaluation (Analysis)

Sources: [Keptn SLO guide](https://keptn.sh/stable/docs/guides/slo/), [AnalysisDefinition reference](https://keptn.sh/stable/docs/reference/crd-reference/analysisdefinition/) and [keptn-contrib/dynatrace-service#728](https://github.com/keptn-contrib/dynatrace-service/issues/728), all read 2026-10-17. Keptn's docs are not gone: the guide is live, with a date of November 4, 2024 near the bottom. It describes the current Analysis feature, which it calls "similar to the functionality provided by the Keptn v1" Quality Gates, and it offers converters for "most" v1 SLIs and SLOs. It does not say that v1 Quality Gates are deprecated (https://keptn.sh/stable/docs/guides/slo/, read 2026-10-17). The v1 quality-gate pages, which hold the `comparison` block and `key_sli`, were not tried.
- *Criterion.* "A Service Level Input (SLI) identifies the data to be analysed as a query to a data provider", and an SLO sets quality criteria for each SLI (https://keptn.sh/stable/docs/guides/slo/, read 2026-10-17). An `AnalysisDefinition` lists `objectives[]`, each with an `analysisValueTemplateRef` (the query), a `target` holding `failure` and `warning` conditions, a `weight` and a `keyObjective` flag. The operators are `lessThan`, `lessThanOrEqual`, `greaterThan`, `greaterThanOrEqual`, `equalTo`, and `inRange`/`notInRange` with `lowBound` and `highBound` (https://keptn.sh/stable/docs/reference/crd-reference/analysisdefinition/, read 2026-10-17). As in SonarQube, the condition states the failure: the guide's example says "The objective fails if the percentile 95 is less than 600" (https://keptn.sh/stable/docs/guides/slo/, read 2026-10-17).
- *Settled.* Three outcomes: "At the end of the analysis, the status returns whether your objective failed, passed, or passed with a warning" (https://keptn.sh/stable/docs/guides/slo/, read 2026-10-17). An objective with no `failure` or `warning` value passes (https://keptn.sh/stable/docs/reference/crd-reference/analysisdefinition/, read 2026-10-17).
- *Missing or noisy.* Neither docs page says what happens when a value cannot be retrieved. The only evidence read is the user report below, from the v1 path.
- *Baseline.* None on the pages read: objectives are compared with fixed thresholds or ranges written in the resource (https://keptn.sh/stable/docs/reference/crd-reference/analysisdefinition/, read 2026-10-17). Keptn v1's comparison with previous evaluation results was not read.
- *Partial success.* Weighted, with a gate. `weight` is "used to emphasize the importance of one objective over others". `totalScore` holds `passPercentage` and `warningPercentage`; the guide's example needs "an overall score of 90% to pass or 75% to get a warning". With `keyObjective: true`, "the entire analysis fails if this particular objective fails" whatever the score (https://keptn.sh/stable/docs/reference/crd-reference/analysisdefinition/ and https://keptn.sh/stable/docs/guides/slo/, both read 2026-10-17). Neither page says how many points a passed or warned objective earns.
- *User-reported failure mode.* With the Dynatrace SLI provider on Keptn v1, a query that returned no data failed the evaluation (the example payload shows `"result": "fail"`). The only message was "Metrics query result has no data", which "doesnt tell the user anything which metric query resulted in no data" and was "the only message that will be shown in the bridge indicating why the evaluation failed". The maintainer's fix names the metric in each indicator's message and sets the result to `warning`, not `fail`, when indicators fail only because they did not return a single value. It closed on 2022-03-08 through PR #733, and the repository was archived on 2024-01-12 (https://github.com/keptn-contrib/dynatrace-service/issues/728, read 2026-10-17).

**Takeaways for the family (inference, not a source claim).**
1. Keptn's form is the same as Kayenta's: weighted objectives scored against pass and warning thresholds, with a `keyObjective` hard gate that overrides the score. It supports D2's required-versus-weighted split, and a warning band is a third state between pass and fail.
2. Keptn v1 first treated no data as a failure, then changed it to a warning that names the query. That is a vendor reaching D1's `inconclusive` with a reason by itself, through a state not built for it.
3. The current Analysis has no relative comparison on the pages read; a baseline would have to live in the query. D4's frozen `at_start` baseline is not something Keptn's current spec shows.

**Takeaways for section 2 (inference, not a source claim).** The SRE workbook treats success over time as a budget: graded, spendable and read over a window, with a policy for when it is spent. That is the strongest source read so far for D5's reconcile-side reading of standing objectives. It suggests a budget or k-of-N over a window as well as, or instead of, a plain streak. Too-few-events is the noisy case in both the workbook and Pyrra, and Keptn's v1 history shows no data drifting from fail to warning. Both support an explicit `inconclusive` state with a reason. OpenSLO's spec fields (`timeWindow`, `budgetingMethod`) are still unread, so the case for rolling against calendar windows and occurrences against timeslices rests on the workbook alone.

### Codecov status checks

Sources: [commit status](https://docs.codecov.com/docs/commit-status), [comparing commits](https://docs.codecov.com/docs/comparing-commits) and [codecov/feedback#861](https://github.com/codecov/feedback/issues/861), all read 2026-10-17. The separate codecov.yml reference page was not read; see Read and not read.
- *Criterion.* Two status checks are configured in `codecov.yml`. `codecov/project` "measures overall project coverage and compares it against the base of the pull request or parent commit". `codecov/patch` "only measures lines adjusted in the pull request", or in the single commit when there is no pull request. Each takes a `target` and a `threshold`, and can be scoped by `branches`, `flags` and `paths` (paths and flags are listed for patch on that page) (https://docs.codecov.com/docs/commit-status, read 2026-10-17).
- *Settled.* `target` is either `auto` (the default) or a number such as `75%`. `auto` "will use the coverage from the base commit (pull request base or parent commit)", so the check fails if coverage drops below the base. `threshold` lets coverage "drop by `<number>%`" and still post `success`. `if_ci_failed` is `error` by default, which sets success only if CI passed; `success` ignores the CI result. The page contradicts itself here: the text lists `success` and `error`, but a YAML comment lists `success, failure, error, ignore`. The `base` option is marked "Deprecated as of July 2020" with no replacement described (https://docs.codecov.com/docs/commit-status, read 2026-10-17).
- *Missing or noisy.* There are three separate cases:
  - **No report for the head commit.** `if_not_found` defaults to `success`, so a commit with no uploaded coverage passes the check unless the author sets `failure` (https://docs.codecov.com/docs/commit-status, read 2026-10-17).
  - **Flag coverage not uploaded on this commit.** `flag_coverage_not_uploaded_behavior` is `include` (process normally, which with carryforward means checking carried-forward numbers), `exclude` (send no check) or `pass` (pass automatically) (https://docs.codecov.com/docs/commit-status, read 2026-10-17).
  - **No report for the base commit.** "Codecov only chooses commits that have successful CI builds" as a base. When the git base has no coverage (a `[ci skip]` commit, a merge commit), Codecov "will seek a parent commit and offset the report to get an approximate base report", a pseudo-comparison. With `allow_pseudo_compare: False` it instead renders "an error in the UI" (https://docs.codecov.com/docs/comparing-commits, read 2026-10-17). Neither page says what the status check itself reports when no base can be found.
- *Baseline.* Relative by default: `target: auto` compares against the base commit's coverage, and `threshold` is the tolerance on the drop. The base is the pull request base, moved forward after a rebase, or the nearest ancestor with a successful build. It is not a frozen baseline: it moves with the base branch (https://docs.codecov.com/docs/comparing-commits, read 2026-10-17).
- *Partial success.* None. Each status is pass or fail, plus a separate "changes" status for coverage changes outside the diff. `informational: true` posts a status that "will pass no matter what the coverage is", the same shadow mode as Argo's `dryRun` and promptfoo's `weight: 0` (https://docs.codecov.com/docs/commit-status, read 2026-10-17).
- *User-reported failure mode.* After a 40-PR batch merged to main, an upload showed "Missing base commit" and a flag's coverage was not carried forward from the nearest covered ancestor. The reporter calls it intermittent and tied to "merge-heavy batches + partial/intermittent flag uploads"; another user said they were "currently experiencing this". The issue is open with no maintainer explanation (https://github.com/codecov/feedback/issues/861, read 2026-10-17). It does not say which status the checks posted.

**Takeaways for the family (inference, not a source claim).**
1. Codecov's defaults make "not measured" a pass: `if_not_found: success` for a missing head report and `pass` as an option for missing flag uploads. That is the opposite of SWE-bench (section 4), where a missing test is a failure. D4 should not copy these defaults.
2. A relative target needs a defined base. Codecov's base moves and is sometimes approximated (pseudo-comparison), and users hit "Missing base commit" in practice. This supports D4's frozen `baseline: at_start` and an `inconclusive` state when no baseline exists.
3. Gating coverage on the CI result (`if_ci_failed: error`) is the default: a measurement from a failed build is not trusted.

### GitHub required status checks

Sources: [about protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches) and [troubleshooting required status checks](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/troubleshooting-required-status-checks), both read 2026-10-17. The troubleshooting page returned 404 at its old path under `managing-protected-branches/` and was read at the path above.
- *Criterion.* A branch protection rule names required checks, each a check run or a commit status, by name. Optionally it names the app expected to set each one: if "the status is set by any other person or integration, merging won't be allowed" (https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches, read 2026-10-17).
- *Settled.* Required checks "must have a `successful`, `skipped`, or `neutral` status" before a merge. In strict mode ("Require branches to be up to date before merging") the branch must also be up to date with the base; in loose mode it need not be, and the page warns that checks "may fail after you merge" (https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches, read 2026-10-17). Checks must pass on the latest commit: "Checks from earlier commits don't satisfy the requirement". When a check and a commit status share a name, both must pass (https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/troubleshooting-required-status-checks, read 2026-10-17).
- *Missing or noisy.* A required check that never reports blocks the merge indefinitely, shown as "Waiting for status to be reported". The troubleshooting page gives these causes:
  - a workflow skipped by path filtering, branch filtering or commit message, whose checks "stay in a "Pending" state and block merging";
  - a run from an ineligible trigger: a `workflow_dispatch` run does not count even when it passes;
  - a merge queue without the `merge_group` trigger, where the check is never reported and the merge fails.

  A job skipped by a job-level `if` condition is the opposite case: "The job reports "Success"" and does not block. A job skipped because a job it depends on failed "may not block merging". The page's advice is "Avoid requiring workflows that can be skipped" and to use `always()` with `needs` for a required job (https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/troubleshooting-required-status-checks, read 2026-10-17). Neither page covers flaky checks or reruns.
- *Baseline.* None. A check is a verdict on one commit (or on the test merge commit when that commit has a status); any comparison with the base happens inside the check, as in Codecov above.
- *Partial success.* None. Every required check must be in a passing state; there are no weights.
- *User-reported failure mode.* Not read from an issue thread: a search of GitHub community discussions returned only pinned posts. The troubleshooting page itself describes the reported symptom: a pull request that touches only root files is blocked forever because a required workflow limited to `scripts/**` never runs. The same page shows the silent-pass twin: a required job whose `if` is false reports success without running anything.

**Takeaways for the family (inference, not a source claim).**
1. GitHub has two behaviours for "did not run", depending on how the skip happened: pending forever (blocks) or `skipped` counted as a pass. A verifier that did not run must have one state, `inconclusive: not_run` (D7), whatever the reason, and it must never count as met.
2. "Never reports" needs a bound. Waiting forever is how GitHub fails safe, but it leaves the pull request stuck; reconcile needs a timeout that turns a missing measurement into a reported `inconclusive` with a reason, not a silent wait.
3. Pinning the source of a result (the expected app) is GitHub's anti-spoofing rule; it matches D7's audit of which verifier produced each measurement and the rejection of third-party verifiers.
4. A result applies only to the commit it was measured at. That supports D7's rule that each measurement records its commit.

### SonarQube quality gates

Sources: [quality gates (fudge factor)](https://docs.sonarsource.com/sonarqube-server/latest/instance-administration/analysis-functions/quality-gates/), [introduction to quality gates](https://docs.sonarsource.com/sonarqube-server/quality-standards-administration/managing-quality-gates/introduction-to-quality-gates) and [community thread 70588](https://community.sonarsource.com/t/quality-gates-passes-without-showing-code-coverage-for-some-of-the-pull-requests/70588), all read 2026-10-17. The first page covers only the fudge factor.
- *Criterion.* A quality gate is a list of conditions. Each one "is a combination of" a metric, a comparison operator and an error value, for example Blocker issue `>` 0, "No blocker issues". Each condition applies "either to new code or overall code". The default gate, Sonar way, has four conditions, all on new code: no new issues, all new Security Hotspots reviewed, new-code coverage at least 80.0%, and new-code duplication at most 3.0% (https://docs.sonarsource.com/sonarqube-server/quality-standards-administration/managing-quality-gates/introduction-to-quality-gates, read 2026-10-17).
- *Settled.* The gate passes or fails: "If one of the conditions is met, the quality gate fails." The condition states the failure, not the target. On a branch both kinds of condition apply. On a pull request "Only conditions defined on *new code* are applied" (https://docs.sonarsource.com/sonarqube-server/quality-standards-administration/managing-quality-gates/introduction-to-quality-gates, read 2026-10-17). Neither page mentions a warning state.
- *Missing or noisy.* The fudge factor: conditions on duplication are ignored until there are at least 20 new lines, and conditions on coverage until there are at least 20 new lines to cover. It is on by default, can be turned off for the instance, and a project administrator can override it (https://docs.sonarsource.com/sonarqube-server/latest/instance-administration/analysis-functions/quality-gates/, read 2026-10-17). So a small change passes those conditions without being measured. Neither page says what happens with no analysis, an empty new code period, or a metric that was not computed.
- *Baseline.* Built in through "new code". On a pull request, new code is "whatever has changed relative to the target branch". On a branch it is set by the branch's new code definition, which lives on a separate page I did not read (https://docs.sonarsource.com/sonarqube-server/quality-standards-administration/managing-quality-gates/introduction-to-quality-gates, read 2026-10-17). Conditions on new code are SonarQube's form of a relative target: they judge only the change, not the whole codebase.
- *Partial success.* None. Every condition is a hard gate; there are no weights or scores.
- *User-reported failure mode.* On SonarQube Cloud, some pull requests showed coverage as "–" instead of a percentage while their quality gate passed. Others in the same TypeScript project on CircleCI showed coverage and gated as expected. The reporter asked whether Sonar was "not receiving the test reports for some of the Pull requests". The only staff reply asks for a screenshot, so the cause is not confirmed (https://community.sonarsource.com/t/quality-gates-passes-without-showing-code-coverage-for-some-of-the-pull-requests/70588, read 2026-10-17). The search listing that led to this thread also shows titles such as "Sonar scan passes with 0 coverage on new code with QG asking for >90" and "New Code always 0 for PRs", but I read only their titles and one-line summaries.

**Takeaways for the family (inference, not a source claim).**
1. Measuring only the change (new code) is a simple, widely deployed form of relative target with no stored baseline number. It fits a delivery criterion ("coverage of changed lines at least N%") as well as D4's frozen `at_start` baseline does, and it cannot drift.
2. The fudge factor is a minimum sample in all but name. SonarQube resolves too-few-lines as a pass, which is why a missing coverage report can look like success. D4's `min_samples` should yield `inconclusive: too_few_samples`, shown to the person as such.
3. A metric shown as "–" and a gate shown as passed in the same view is the failure D1's states exist to prevent: the criterion state must say `inconclusive` whenever the value is absent.

**Takeaways for section 3 (inference, not a source claim).** All three systems resolve some form of "not measured" as a pass by default: Codecov's `if_not_found: success`, GitHub's `if`-skipped job reported as success, and SonarQube's fudge factor. GitHub's path-skipped workflow fails the other way, blocking forever. None of them has a first-class inconclusive state, and the user reports above come from that gap. This is direct support for D1's `inconclusive` state with a reason, for D4's `min_samples` and frozen baseline, and for D7's rule that a verifier that did not run is never met.

## 4 Agent and LLM evaluation

All sources below were read on 2026-10-16 through a fetch tool that summarises each page against a question. A later action should confirm the exact wording before quoting.

**Inspect AI scorers, scoring policy and reducers.** Sources: [scorers](https://inspect.aisi.org.uk/scorers.html), [scorer reference](https://inspect.aisi.org.uk/reference/inspect_ai.scorer.html) and [scoring policy](https://inspect.aisi.org.uk/scoring-policy.html).
- *Criterion.* A scorer returns a `Score` with a `reason` and a value. The value is a grade (`CORRECT` "C", `INCORRECT` "I", `PARTIAL` "P" or `NOANSWER` "N"), a number, or a list or dict. Built-in text scorers set reasons such as `no_response` and `invalid_response_format`.
- *Settled.* Metrics such as `accuracy`, `mean` and `stderr` run over all samples. `value_to_float()` maps C to 1.0, I to 0, P to 0.5 and N to 0. It casts numbers directly, and lists and dicts log a warning and become 0.
- *Missing or noisy.* There are four distinct cases:
  - NOANSWER (an empty completion or a refusal) scores 0 and stays in the denominator.
  - `Score.unscored()` is NaN. Metrics exclude it, and it is counted as `unscored_samples` after epoch reduction.
  - A scorer that raises records `sample.error`, and the sample drops out of the metric.
  - A scorer that returns `None` adds nothing and is not counted as unscored.
- *Repeated runs.* Noise is handled by epochs: each sample runs N times and a reducer collapses the results. The reducers are `mean_score` (the default), `median_score`, `mode_score`, `max_score`, `at_least(k, value)`, `pass_at(k)` (the probability that at least one of k attempts succeeds) and `pass_k(k)` (the probability that all k succeed).
- *Baseline.* The scorer model has none. Comparing runs happens outside it.
- *Partial success.* PARTIAL scores 0.5 by default, and numeric scores can carry any fraction.
- *Failure mode.* This comes from the scoring-policy page, not from an issue thread. The default `mean` reducer converts NOANSWER to 0.0 "before metrics run, erasing the label". A sample with one correct and one unscored epoch reduces to 1.0. So after reduction, "not measured" can silently become a pass or a fail. The scorer reference also contradicts itself on whether `at_least` needs values greater than or equal to `value` or strictly greater.

**SWE-bench harness grading.** Source: [swebench/harness/grading.py](https://github.com/SWE-bench/SWE-bench/blob/main/swebench/harness/grading.py).
- *Criterion.* Each instance has two named test lists. FAIL_TO_PASS tests must go from failing to passing, and PASS_TO_PASS tests must keep passing.
- *Settled.* The harness runs the tests and parses the log; no model judges. `get_resolution_status` returns FULL when both pass fractions are 1, PARTIAL when F2P is between 0 and 1 (exclusive) and P2P is 1, and NO otherwise. An instance is `resolved` only when it is FULL. An empty list counts as 1.
- *Missing or noisy.* An unusable log means the instance is not resolved. `get_logs_eval` returns `({}, False)` when:
  - the log shows an apply-patch, reset, test-error or timeout code;
  - the start or end output marker is missing;
  - nothing parses and nothing shows that the suite ran; or
  - the command exits non-zero while no failure is reported.

  An advisory `infra_failure` flag is recorded but does not change the outcome. A test missing from the parsed log does not count as passed: `test_passed` returns False and `test_failed` returns True. A skipped F2P test counts as failed, and a skipped P2P test counts as maintained. A `None` patch stops grading early with `patch_is_None`.
- *Baseline.* It is built in: F2P and P2P are themselves a before-and-after comparison against the repository at its base commit.
- *Partial success.* PARTIAL is reported but never counts as resolved.
- *Failure mode.* This comes from a code comment, not an issue thread. Under `EvalType.FAIL_ONLY` a missing test counts as a success, and the "suite never ran" check exists precisely to stop an empty log from passing.

**promptfoo assertions.** Source: [assertions and metrics](https://www.promptfoo.dev/docs/configuration/expected-outputs/).
- *Criterion.* An `assert` entry has these fields:
  - `type`, for example `equals`, `contains`, `llm-rubric`, `cost` or `javascript`;
  - `value`;
  - an optional `threshold`, for types that produce a score, such as `similar` and `cost`;
  - `weight`, which defaults to 1.0; and
  - `metric`, a named tag that the UI aggregates.

  Any type can be negated with a `not-` prefix.
- *Settled.* The test score is the weighted average of the assertion scores.
  - With no test-level `threshold`, every assertion with non-zero weight must pass.
  - With a threshold, the test passes when the weighted score reaches it, even if some assertions failed.
  - An `assert-set` groups child assertions and has its own weight and metric. Either all its children must pass, or, with a set `threshold`, enough of them must (0.5 means half).
- *Missing or noisy.* For negated model-graded types, a grader error or a missing verdict stays a failure with score 0, because negation inverts only a valid verdict. Configuration errors also still fail under negation. This page does not cover repeated runs.
- *Baseline.* This page does not cover it. Comparison happens across providers or prompts in the results matrix, which I did not read.
- *Partial success.* Scores are weighted averages. `weight: 0` records a metric without letting it gate, which is the same shadow mode as Argo's `dryRun` in section 1.
- *Failure mode.* Not read from an issue thread. In the docs' own example, the weighted average lets a passing weight-1 `contains` partly offset a failed weight-2 `equals` (score 0.33). With a test-level threshold at or below that score, the test would pass. This is the hazard of mixing gates with weights.

**Takeaways for the family (inference, not a source claim).**
1. Karakuri's `Met bool` collapses four outcomes that Inspect keeps apart: wrong (0), no answer (0, kept in the denominator), unscored (excluded and counted) and errored (excluded and recorded). The proposal's "not measured, with a reason" matches `unscored`, but the reason has to survive aggregation, and Inspect shows that a reducer can erase it.
2. SWE-bench is the closest analogue to a delivery criterion: a deterministic before-and-after test contract. An unusable log, a missing test or an infrastructure error means "not resolved", with the cause recorded beside it. PARTIAL is reported but never counts as done.
3. Repetition belongs in the criterion: Inspect's epochs with a named reducer (`pass_at` against `pass_k`) match the count and consecutive-success limits in section 1.
4. promptfoo decides required versus weighted with one rule: without a threshold, every assertion with non-zero weight is required. Weight 0 is a shadow mode.

### CrewAI tasks and guardrails

Sources: [Tasks](https://docs.crewai.com/en/concepts/tasks) and [crewAIInc/crewAI#7150](https://github.com/crewAIInc/crewAI/issues/7150), both read 2026-10-17.
- *Criterion.* Two fields, and only one of them is checked. `expected_output` is a required string, "A detailed description of what the task's completion looks like"; the page does not say that anything compares the output with it. It is prose handed to the agent. The checked criterion is the guardrail. A function guardrail takes the task output as its one parameter and "Should return a tuple of `(bool, Any)`": `(True, value)` on success, `(False, "message")` on failure. A string passed to `guardrail` or `guardrails` becomes an `LLMGuardrail` run on the agent's LLM, which returns `(True, output)` or `(False, feedback)`. `guardrails` takes a list of functions and strings, runs them in order with each receiving the previous one's output, and when set it overrides `guardrail` (https://docs.crewai.com/en/concepts/tasks, read 2026-10-17).
- *Settled.* By the guardrail's boolean. On failure "The error is sent back to the agent", which tries to fix the output, and the task "is retried up to `guardrail_max_retries` times". `guardrail_max_retries` is "Maximum number of retries when guardrail validation fails. Defaults to 3." `max_retries` is deprecated and "will be removed in v1.0.0" (https://docs.crewai.com/en/concepts/tasks, read 2026-10-17). The docs page does not say what happens when the retries run out. The issue below shows the error raised then, "ValueError: Agent's guardrail failed validation after 3 retries" (https://github.com/crewAIInc/crewAI/issues/7150, read 2026-10-17).
- *Missing or noisy.* The docs page does not cover a guardrail that cannot run. Per the issue, `LLMGuardrail.__call__` "catches every exception and returns (False, "Error while validating the task output: ...")", so a provider outage looks like a failed validation, is fed back to the agent as feedback and spends a retry (https://github.com/crewAIInc/crewAI/issues/7150, read 2026-10-17).
- *Baseline.* None on the page read. A guardrail judges one output by itself.
- *Partial success.* None. A guardrail returns a boolean; the `Any` beside it carries the (possibly transformed) output or the feedback, not a score.
- *Done against succeeded.* A task is done when the agent returns an answer that every guardrail accepts; the page gives no other definition of completion, and its callback runs "after the task is completed". With no guardrail, done means the agent stopped, and `expected_output` was never checked.
- *User-reported failure mode.* A guardrail that could not run is reported as a failed one. The reporter says the caller cannot tell an outage from a bad output, and the final `ValueError` blames the output. They proposed a `GuardrailExecutionError` or an `errored: bool` field on `GuardrailResult`, neither appended to the conversation nor counted against `guardrail_max_retries`; another commenter suggested a three-state PASS/FAIL/UNVERIFIED contract. The issue was opened 2026-08-29 and closed as not planned on 2026-10-07 by a stale bot, with no maintainer comment on the page. A linked fix, PR #7151, is described by the author as open, but the page alone does not settle its state (https://github.com/crewAIInc/crewAI/issues/7150, read 2026-10-17).

**Takeaways for the family (inference, not a source claim).**
1. CrewAI's `expected_output` is a judged criterion with no judge: a description the agent reads, settled by nothing. Only a guardrail settles anything. That is the gap D3 closes by giving each criterion a verifier, and the reason a prose-only criterion should show as `inconclusive: not_run`, not as met.
2. The guardrail retry is a loop inside the run: failure feedback goes back to the agent, up to a bound. That fits the loop's own convergence, not reconcile; the verdict reconcile reads is the one after the last retry.
3. Collapsing "could not run" into "failed" is the same loss as Karakuri's `Met bool`, and the issue's proposed PASS/FAIL/UNVERIFIED states are D1's met, unmet and `inconclusive` with a reason. A verifier error must also not count as an attempt or reach the agent as feedback on its work.

### AutoGen AgentChat termination conditions

Sources: [termination tutorial](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/termination.html) and [microsoft/autogen#6826](https://github.com/microsoft/autogen/issues/6826), both read 2026-10-17.
- *Criterion.* A termination condition is "a callable that takes a sequence of BaseAgentEvent or BaseChatMessage objects since the last time the condition was called" and "returns a StopMessage if the conversation should be terminated, or None otherwise". In a group chat team it "is called after each agent responds". The page lists eleven built-ins: MaxMessageTermination, TextMentionTermination, TokenUsageTermination, TimeoutTermination, HandoffTermination, SourceMatchTermination, ExternalTermination, StopMessageTermination, TextMessageTermination, FunctionCallTermination and FunctionalTermination. Three of them as the page describes them: MaxMessageTermination "Stops after a specified number of messages have been produced, including both agent and task messages" (example `max_messages=3`); TextMentionTermination "Stops when specific text or string is mentioned in a message (e.g., "TERMINATE")" (example `TextMentionTermination("APPROVE")`); ExternalTermination "Enables programmatic control of termination from outside the run", with no parameters or example on the page (https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/termination.html, read 2026-10-17).
- *Settled.* By the first condition that returns a StopMessage. Conditions "can be combined using the AND and OR operators". The page's OR example stops "either after 10 messages are generated or when the critic agent approves a message"; for AND, "if we want to stop the run only when both conditions are met, we can use the AND (`&`) operator". The page does not say how AND tracks two conditions met at different calls. Conditions "are stateful but reset automatically after each run"; once reached, one "must be reset by calling reset() before it can be used again" (https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/termination.html, read 2026-10-17).
- *Missing or noisy.* Not on the page. It does not say what happens with no condition set, only that "a run can go on forever, and in many cases, we need to know *when* to stop them" (https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/termination.html, read 2026-10-17).
- *Baseline.* None. A condition reads the messages since its last call; nothing compares the run with an earlier state.
- *Partial success.* None. A condition stops the run or does not.
- *Done against succeeded.* The run is done when any condition fires, and nothing in the result says whether the task succeeded. `TaskResult.stop_reason` is a string, for example "Maximum number of messages 3 reached, current message count: 3", "Text 'APPROVE' mentioned" or "Function 'approve' was executed."; the page defines no field or flag that tells a limit from an approval, so a caller has to parse the text (https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/termination.html, read 2026-10-17). In the OR example, an approval and ten unapproved messages end the run the same way.
- *User-reported failure mode.* The stop word in the task ended the run before any agent spoke. With `TextMentionTermination("END_FEEDBACK_DISCUSSION")` and the phrase in the initial user message, the team stopped at once with `stop_reason="Text 'END_FEEDBACK_DISCUSSION' mentioned"`. The reporter's workaround was to explain the phrase in the prompt rather than quote it, which "worked, but does not seem intuitive". A user suggested a subclass restricted by `sources=`; the only reply from the team, by ekzhu on 2025-09-16, says "We recommend you to create your own class of termination conditions." Reported against AutoGen 0.6.2, opened 2025-07-17, and still open with the `needs-triage` and `Bug` labels (https://github.com/microsoft/autogen/issues/6826, read 2026-10-17).

**Takeaways for the family (inference, not a source claim).**
1. AutoGen's termination conditions decide when a run stops, not whether it succeeded. A budget (messages, tokens, time) and a success signal (an approval, a function call) are the same type, joined by OR, and only a free-text `stop_reason` tells them apart. Karakuri's run outcome needs the two kept apart: a run that hit its budget is done but not met.
2. `TextMentionTermination("APPROVE")` is a judged criterion settled by a word in the transcript, and the issue shows the word can come from the task itself. A criterion's verdict must come from a named verifier, not from text anywhere in the run, which is D7's rule on who produced each measurement.
3. AND over stateful conditions is how AutoGen says "all of these", but the page leaves its timing open. D2's "every required criterion met" should be evaluated over one state of the world, not over flags latched at different moments.

### LangGraph recursion limit and END

Sources: [Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api) and [langchain-ai/langgraph#9163](https://github.com/langchain-ai/langgraph/issues/9163), both read 2026-10-17.
- *Criterion.* None in the framework. `END` is "a special node that represents a terminal node", and a conditional edge can "optionally route to one or more edges (or optionally terminate)". The router that returns `END` is the author's code, so whatever it tests is the only criterion (https://docs.langchain.com/oss/python/langgraph/graph-api, read 2026-10-17).
- *Settled.* By routing, bounded by a step limit. "The graph execution terminates when all nodes are `inactive` and no messages are in transit." "The recursion limit sets the maximum number of super-steps the graph can execute during a single execution"; "Starting in version 1.0.6, the default recursion limit is set to 1000 steps". It "is a standalone `config` key and should not be passed inside the `configurable` key", for example `config={"recursion_limit": 5}`. "Once the limit is reached, LangGraph will raise `GraphRecursionError`" (https://docs.langchain.com/oss/python/langgraph/graph-api, read 2026-10-17).
- *Missing or noisy.* Not on the page. Its nearest topic is the limit itself: it offers a reactive approach, catching the error outside the graph, and a proactive one, where "LangGraph provides a `RemainingSteps` managed value that tracks how many steps remain before hitting the recursion limit", which "allows for graceful degradation within your graph". The page does not say whether state is returned with the error (https://docs.langchain.com/oss/python/langgraph/graph-api, read 2026-10-17).
- *Baseline.* None. State is the graph's own; nothing compares it with a reference.
- *Partial success.* None in the framework. The proactive pattern ends a run that ran out of steps through the same `END` as one that finished its work.
- *Done against succeeded.* Reaching `END` means the run stopped normally; it does not mean the task succeeded. In the page's own proactive example the router returns `END` when `remaining_steps <= 2`, and the result is "Graph completes normally (no exception)". The reactive approach turns the same situation into an exception. Neither carries a success flag (https://docs.langchain.com/oss/python/langgraph/graph-api, read 2026-10-17).
- *User-reported failure mode.* A graph that finished is reported as having hit the limit. With `recursion_limit` 2 and `START -> a -> b` on an `InMemorySaver`, both nodes run, the checkpoint shows the final state (`state: {'n': 2} next: ()`), and the run still raises "Recursion limit of 2 reached without hitting a stop condition. You can increase the limit by setting the `recursion_limit` config key." The reporter traces it to `if self.step > self.stop` in `pregel/_loop.py`, which "runs before the next tasks are prepared, so the loop reports `out_of_steps` even when nothing is left to run". Reproduced on LangGraph 1.2.12 and on main at b36b1d5; opened 2026-10-01 and open, with no maintainer reply, no linked pull request and a fix commit (10cf901) on the reporter's fork (https://github.com/langchain-ai/langgraph/issues/9163, read 2026-10-17).

**Takeaways for the family (inference, not a source claim).**
1. LangGraph has a terminal state and a step budget and nothing else. Success is whatever the author's router tests, and the recommended graceful path routes a run that ran out of steps to the same `END` as one that finished. That is the conflation Karakuri's loop must avoid: converged, out of budget and criteria met are three separate facts.
2. The issue shows the mirror of the silent pass: a run whose work is complete is reported as failed because the budget check reads the counter, not the remaining work. A criterion should be settled from the state the run left (here, the checkpoint), not from how the run ended.
3. A step limit that can be raised by config is a budget, not a criterion. Reconcile can retry a run that hit its budget, but should not read that retry as evidence about the criteria.

**Takeaways for section 5 (inference, not a source claim).** None of the three frameworks has a notion of success apart from stopping. CrewAI comes closest: a guardrail's boolean, retried with feedback to the agent, which still turns an error into a failure. AutoGen and LangGraph stop on the first of a set of conditions or on a terminal node, and put budget stops and success stops through the same path, told apart only by a free-text `stop_reason` or by which exception was raised. All three user reports are cases where the end of the run says something false about the work: an outage reported as a bad output, a stop word in the prompt ending the run before work began, and a finished graph reported as out of steps. For Karakuri this supports keeping the run's outcome (converged, budget spent, errored) apart from each criterion's state (met, unmet, `inconclusive` with a reason), and settling criteria from the world after the run, by verifiers, never from how the run ended.

## 6 Acceptance-criteria practice

### Cucumber Gherkin reference

Sources: [Gherkin reference](https://cucumber.io/docs/gherkin/reference), [cucumber/cucumber-jvm#1946](https://github.com/cucumber/cucumber-jvm/issues/1946) and [cucumber/common#12](https://github.com/cucumber/cucumber/pull/12), all read 2026-10-17. The search result for the third gave a `cucumber/cucumber/pull/12` URL; the page it opened is titled as cucumber/common issue #12.
- *Criterion.* A scenario (the keyword `Scenario` "is a synonym of the keyword `Example`") is a list of steps. "`Given` steps are used to describe the initial context of the system", "`When` steps are used to describe an event, or an _action_", and "`Then` steps are used to describe an _expected_ outcome, or result". The outcome "_should_ be on an **observable** output": "You should only verify an outcome that is observable for the user (or external system)". The page recommends "3-5 steps per example" and warns that "Having too many steps will cause the example to lose its expressive power". `Rule` groups scenarios under "one _business rule_ that should be implemented". The page does not say "one behaviour per scenario"; that phrase is not on it (https://cucumber.io/docs/gherkin/reference, read 2026-10-17).
- *Settled.* By code, not by the text. Each step is matched to a step definition, and "Keywords are not taken into account when looking for a step definition", so two steps with the same text but different keywords cannot coexist. The `Then` step definition "should use an _assertion_" to compare actual and expected results (https://cucumber.io/docs/gherkin/reference, read 2026-10-17). The scenario is the prose criterion; the step definitions are its verifier.
- *Missing or noisy.* The reference page does not say what happens when a step has no definition. The cucumber-jvm maintainer states the rule: "When strict mode is enabled PENDING and UNDEFINED are mapped to FAILED, otherwise they're mapped to SKIPPED", and Maven in turn maps SKIPPED to PASSED (https://github.com/cucumber/cucumber-jvm/issues/1946, read 2026-10-17). So without strict mode a criterion with no verifier behind it ends up green. In 2015 a cucumber-js maintainer asked "What is the reasoning behind undefined/pending steps exiting with status zero?"; another participant's team kept non-strict mode on purpose so that pending steps against downstream services they did not control turned scenarios yellow without failing the build. The thread closed on 2016-12-17 with "The next version of cucumber-js is going to have strict as the default with a CLI option for `--no-strict`". The thread names only cucumber-js as changing (https://github.com/cucumber/cucumber/pull/12, read 2026-10-17). Noise and repeated runs are not on any page read.
- *Baseline.* None on the pages read. A `Background` "allows you to add some context to the scenarios that follow it" and runs before each one. The page says to keep it "**short**" and not to use it for "**complicated states**" unless the client needs to know that state; there can be only one per `Feature` or `Rule` (https://cucumber.io/docs/gherkin/reference, read 2026-10-17). It is shared setup, not a reference measurement.
- *Partial success.* None within a scenario. A `Scenario Outline` is a template with `< >` parameters, and it "is run _once for each row_ in the `Examples` section beneath it"; Cucumber replaces the parameters with the row's values before matching steps (https://cucumber.io/docs/gherkin/reference, read 2026-10-17). Each row is a separate pass-or-fail result. The page gives no weights and no aggregate score.
- *User-reported failure mode.* Undefined steps reported as passed. With cucumber-jvm 5.6.0 and `strict=true`, a user's HTML report showed undefined steps as passed, and with `strict=false` it also showed them as passed rather than skipped. The maintainer traced it to the third-party report plugin, which "does not implement `io.cucumber.plugin.StrictAware`" and so mapped the statuses to passed whatever the strict setting. The issue was opened and closed as completed on 2020-04-16 (https://github.com/cucumber/cucumber-jvm/issues/1946, read 2026-10-17).

**Takeaways for the family (inference, not a source claim).**
1. Gherkin splits a criterion into a sentence a person writes and code that settles it, which is the split between a criterion and its verifier in D3. The prose alone settles nothing.
2. A step with no definition is Cucumber's form of "not measured", and for years its default was to skip it, which build tools then counted as a pass. That is the same silent pass as Codecov's `if_not_found: success` (section 3). It supports D1's `inconclusive: not_run` and D7's rule that a criterion naming a verifier that did not run is never met. The jvm report shows the state can still be lost downstream, in a report that does not know about it.
3. "Observable for the user (or external system)" is a rule a create-time check cannot enforce, but a person writing a judged criterion can follow it, and the judge can be told to reject a criterion that is not observable.
4. `Scenario Outline` with `Examples` is one criterion run over a table of inputs, each row its own result. It is a deterministic form of D4's `samples` with the `all` reducer.

**Takeaways for the family (inference, not a source claim).**
1. An OKR grade is a progress score, not a completion rule. A 0.6 to 0.7 average is the expected outcome, so an OKR-style key result maps to D2's `required: false` weighted criterion, never to a required gate, and a person should not expect an objective with stretch targets to complete.
2. OKRs are the one practice read so far where the score is meant to stay below 1.0. That supports keeping D2's `weight` as progress for reconcile to read, apart from `required`; mixing the two would make a 0.7 grade either a failure or a pass, and both are wrong here.
3. Key results are graded by people at a meeting, with an owner explaining the grade. That is a judged criterion with a named judge. Karakuri's `judged` kind has the model as judge, so the "evidence of completion" rule matters more: a judged criterion should name the evidence the judge will look at.
4. "By xx%" key results need a baseline the guide never defines. That is D4's `baseline: at_start`, which the guide's own example leaves open.

**What these practices say about how a person writes a criterion (inference, not a source claim).** Both sources address the person writing the criterion, not the code that settles it, and they agree. Gherkin says the expected outcome goes in `Then`, must be "**observable**" to "the user (or external system)", and is settled by an assertion; it keeps a scenario to "3-5 steps", runs one behaviour over many inputs with `Scenario Outline` and `Examples`, and keeps shared setup in a short `Background`. The page does not use the words "one behaviour per scenario"; the closest it comes is 3-5 steps and one `Rule` per business rule. The OKR guide says a key result is "measurable", "easy to grade with a number", an outcome and not an activity, backed by "evidence of completion", and few in number (about three per objective); the objective must be "obvious to an observer". For D6 this means: (a) the create-time checks D6 lists cover only the machine fields of `measured` and `verified` criteria, and nothing checks the prose of a `judged` criterion. Both practices would ask that a judged criterion name an observable outcome and the evidence that shows it, and not describe an activity ("review", "help", "analyze"). (b) D6's `--criteria-file` should have room for one criterion per observable outcome, not one criterion holding several. (c) A criterion with no verifier behind it is Gherkin's undefined step: D6's display should show it as `inconclusive: not_run`, never as met, since that is the silent pass both cucumber threads describe. (d) A stretch target written OKR-style belongs in a `required: false` criterion with a weight, shown as progress, so a person reading the objective page sees 0.7 as expected and not as failure. D6 was written before this section; these practices back its shape and add the prose rules in (a), which it lacks.

## 7 Measurement statistics for noisy metrics

All sources below were read on 2026-10-16.

**Luo, Hariri, Eloussi and Marinov, "An Empirical Analysis of Flaky Tests", FSE 2014.** Source: [PDF](https://mir.cs.illinois.edu/lamyaa/publications/fse14.pdf). I read pages 1 to 3 as rendered page images: the introduction, Table 1 (findings) and Table 2 (categories).
- *What a flaky test is.* A test whose "outcome is non-deterministic with respect to a given software version": it can pass or fail on the same code.
- *Scale (second-hand).* Through a personal communication with John Micco, the paper reports that Google's TAP system averaged 1.6M test failures a day over 15 months, and 73K of them (4.56%) were caused by flaky tests.
- *Repeated runs and reruns (second-hand for Google).* The paper calls the most common mitigation running a failing test several times and declaring it passing if any run passes. It says that at Google a failing test is rerun 10 times on the same code version, and is labelled flaky if any of those reruns passes. Frameworks offer the same thing through annotations such as Android `@FlakyTest`, Jenkins `@RandomFail` and Spring `@Repeat`. The authors call reruns and exclusion (`@Ignore`) "workarounds" that "waste a lot of machine resources" or reduce coverage.
- *Causes.* 201 commits that fix flaky tests in 51 Apache projects. Async Wait (74), Concurrency (32) and Test Order Dependency (19) are the top three categories; 40 commits were hard to classify (Table 2). 78% of flaky tests are flaky from the first time they are written (F.2). 96% are platform-independent (F.3).
- *Failure mode.* Flaky tests waste debugging time and "may also hide real bugs", because developers learn to ignore their failures. 24% of fixes changed the code under test, and 94% of those fixed a real bug (F.12). So "rerun until green" can mask a real defect.

**Google Testing Blog, "Flaky Tests at Google and How We Mitigate Them" (2016).** Source: [post](https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html). The fetch returned only the comment thread, not the article body, so the article's own figures were not read; see Read and not read.
- A reply from the blog's team says: "Our rerun mechanism is only used for tests that are marked as flaky or when users specifically request it". Another says "a test that fails reliably is far better than a test that is flaky".
- The team also says it does not "keep accurate count of the number of times that flaky tests are really masking bugs".
- Commenters (not Google) report rerunning failures three times, failing only on two consecutive failures, running hundreds of reliability executions and moving tests below a consistency threshold out of CI gating, and soaking new tests in a loop for a week before they gate.

**Cross-reference to section 1 (not re-read).** Argo Rollouts puts repetition into the criterion itself: `count`, `interval`, `failureLimit`, `consecutiveSuccessLimit`, and Inconclusive as a named state. Kayenta compares a canary with a baseline measured at the same time, using a Mann-Whitney U test at 98% confidence and an effect-size tolerance band instead of a fixed threshold. It reports Nodata, and scores 0 when 50% or more of the metrics have no data.

**Takeaways for the family (inference, not a source claim).**
1. A single run of a noisy check is not a measurement. A criterion over a noisy signal needs a repetition policy (N runs, a reducer and a minimum sample), and the policy belongs to the criterion so that the verifier cannot pick it.
2. "Passes if any rerun passes" (Google's rerun rule as Luo et al. report it) is a definition of flakiness, not of success. Used as a success rule, it hides real bugs (F.12). For a gate, `all` or "k of N" with a recorded flake count is safer.
3. Flakiness is itself a metric worth measuring: the proposal's "flaky-test count over N runs" verifier matches the reliability-suite practice the commenters describe.
4. Too few samples should give "inconclusive", not pass or fail, which matches Argo's Inconclusive, Kayenta's Nodata and Inspect's `unscored` (section 4).

## What this means for Karakuri

Sections 2, 3, 5 and 6 held the marker when these decisions were written, so every decision below rests on sections 1, 4 and 7 only and is weaker for it: SLO error budgets, CI gate semantics (Codecov, SonarQube, GitHub required checks), agent frameworks' termination and acceptance-criteria practice were not read. Section 3 was written afterwards (2026-10-17); its takeaways support D1, D4 and D7, and the decisions have not been revised against it.

### D1 Criterion kinds and states

**Decision.** Keep three kinds, settled by three different things: `judged` (a model, from action outcomes, as today), `verified` (a pack verifier's pass or fail) and `measured` (a named number from a pack verifier compared with a target by deterministic code). Replace `Met bool` with a state: `met`, `not_met` or `inconclusive`, and `inconclusive` always carries a reason (`no_data`, `verifier_error`, `too_few_samples`, `not_run`, `unsupported`, `no_baseline`, `measure_changed`). A missing measurement, NaN or an empty result is `inconclusive`, never a pass and never a silent zero. For a gate, `inconclusive` is not `met`, so the objective does not complete, but it also does not count as a failed pass for the breaker; it is reported apart. A verifier error stays a reason under `inconclusive`, not a fourth state: what the gate and the breaker need is that it is told apart from `not_met`, and the reason does that. A `verifier_error` is never handed to the agent as feedback on its work and never counts as an attempt. A criterion's state comes from its verifier reading the world after the run, never from how the run ended. A run that converged, spent its iteration budget or errored is a run outcome, recorded apart from the criterion states, and a run that spent its budget is done but not `met` by that fact alone. Keep `Met` in JSON as derived (`state == met`) so the API does not break.

**Rests on.** Section 1: Argo's Inconclusive and Kayenta's Nodata/NodataFailMetric and the `replace` silent-pass hazard (https://argo-rollouts.readthedocs.io/en/stable/features/analysis/, https://spinnaker.io/docs/guides/user/canary/judge/). Section 1, second pass: Argo keeps "Error", "Failed" and "Inconclusive" as separate unsuccessful stages, and an Inconclusive run pauses the rollout for a person (https://argo-rollouts.readthedocs.io/en/stable/features/specification/, https://argo-rollouts.readthedocs.io/en/stable/features/analysis/). Section 2, Keptn: a query with no data first failed the evaluation, then became a warning that names the query (https://github.com/keptn-contrib/dynatrace-service/issues/728). Section 3, takeaways for section 3: none of Codecov, GitHub or SonarQube has a first-class inconclusive state, and the user reports come from that gap. Section 4: Inspect's four outcomes and the reducer that erases "not measured" (https://inspect.aisi.org.uk/scoring-policy.html); SWE-bench's "unusable log means not resolved, cause recorded" (https://github.com/SWE-bench/SWE-bench/blob/main/swebench/harness/grading.py). Section 5: CrewAI's guardrail that turns an outage into a failed validation and spends a retry, with the PASS/FAIL/UNVERIFIED proposal (https://github.com/crewAIInc/crewAI/issues/7150); AutoGen's free-text `stop_reason` and LangGraph's shared `END`, which send budget stops and success stops through one path (https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/termination.html, https://docs.langchain.com/oss/python/langgraph/graph-api). Section 7, takeaway 4.

**Conflicts.** None with a rule. It changes a core entity, which with D3 is why ADR 029 is needed.

**Changed in the second pass.** The state set itself stays `met`, `not_met` and `inconclusive` with a reason. Section 1's second pass found that Argo keeps Error apart from Failed and Inconclusive, but the pages read do not say what causes an Error or how it counts. Section 3's takeaways and Keptn's no-data history in section 2 show that the harm comes from merging "could not measure" into pass or fail, and the existing `verifier_error` and `no_data` reasons already prevent that. Two rules were added from section 5. From CrewAI #7150 (takeaway 3): a verifier error is not fed back to the agent and does not spend an attempt. From the section 5 takeaways (AutoGen takeaway 1, LangGraph takeaways 1 and 2): the run outcome (converged, budget spent, errored) is kept apart from each criterion's state, and criteria are settled from the world after the run, not from how it ended.

### D2 Required versus weighted, and the completion rule

**Decision.** Every criterion is `required` unless it says otherwise, and completion stays "all required criteria met". `weight` keeps its present role, the progress score that reconcile's score streak reads, and a criterion with `required: false` contributes to the score but cannot block or grant completion. `required: false, weight: 0` is a shadow criterion: evaluated, shown and audited, never gating, so a new verifier can be observed before it gates. No weighted threshold may turn a failed required criterion into completion. "All required criteria met" is read over one state of the world, the states the verifiers settled after the same run, not over flags latched at different moments. **Zero required criteria never completes.** An objective with no required criteria does not complete through the loop. It fails the way an objective with no criteria fails today: the guard at `verify.go:37` publishes `no_success_criteria_defined`, the score stays 0.0 and `finalizeLoop` sets `StatusFailed` (fact 6). The guard is changed to count required criteria rather than all criteria. Otherwise an objective whose criteria are all `required: false` would pass it and complete vacuously at `verify.go:127`. Create also rejects such an objective, so that it does not spend up to `maxIter` iterations before it fails. A stretch target written OKR-style, where a grade of 0.6 to 0.7 is the expected outcome, belongs in a `required: false` criterion with a weight. Its score is shown as progress, never as a gate and never as a failure.

**Rests on.** Section 1: Kayenta's `critical` gate overriding weighted scores, Argo's `dryRun` shadow mode. Section 2, Keptn: `weight`, `totalScore` pass and warning percentages, and `keyObjective`, which fails the whole analysis whatever the score (https://keptn.sh/stable/docs/reference/crd-reference/analysisdefinition/). Section 4: promptfoo's "no threshold means every non-zero-weight assertion is required" and its weighted-average hazard (https://www.promptfoo.dev/docs/configuration/expected-outputs/); SWE-bench's PARTIAL that never counts as resolved. Section 5, AutoGen takeaway 3: AND over stateful conditions leaves its timing open (https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/termination.html). Section 6, re:Work OKRs: key results graded 0.0 to 1.0 by a rough average, with 0.6 to 0.7 expected and full attainment a sign the target was not ambitious enough (https://rework.withgoogle.com/intl/en/guides/set-goals-with-okrs). Code reading, fact 6: the empty-criteria guard at `verify.go:37`, the runner's `criteriaMet` and `finalizeLoop`'s `StatusFailed`, and the closing note that the guard counts all criteria rather than required ones.

**Conflicts.** None. Rule 8 is respected: completion stays a single convergence; anything weighted over time is reconcile's business (D5). `POST /objectives/{id}/status` can still write `completed` outside the loop (fact 6). That is outside this completion rule and is not decided here.

**Changed in the second pass.** The completion rule now states what happens with zero required criteria: the objective never completes, and the guard counts required criteria. The earlier parenthetical rested on fact 1's reading that `metCount == len(criteria)` is true for an empty list. Code reading fact 6 corrected that: an empty list fails at `verify.go:37`, so rejecting such an objective at create time saves wasted iterations rather than preventing a vacuous completion. Fact 6 also found that an all-optional objective would complete vacuously under the current guard. From section 5 (AutoGen takeaway 3), the rule is read over one state of the world. From section 6 (re:Work OKRs, takeaways 1 and 2), an expected-partial score goes in `required: false` and is shown as progress. Section 2's Keptn `keyObjective` confirms the gate-over-weights shape and changed nothing.

### D3 The verifier contract

**Decision.** A verifier is a pack capability that declares, in its pack manifest (Phase 39 / ADR 028), the metrics it can emit: name, unit, direction (higher or lower is better) and typed parameters. That declaration goes beside the existing `OutputSchema` (`capability.go:11`, today only `{Type: "object"}`), not inside a free-form schema, so create-time validation (D6) can read it without interpreting JSON Schema. `ActionResult` gains `Measurements []Measurement{Name, Value float64, Unit, Source}`, a typed field that the gateway carries through MCP results as structured content, so a number is never scraped out of `StateDelta` or prose. Each measurement carries `Trust` (rule 9): a value computed by this deployment's own verifier is first-party; one read from a third-party system (a Datadog query over traffic others generate is still first-party data, a number in a PR comment is not) is marked from what it holds. Rule 10: a verifier that cannot measure returns `ErrUnsupported` or an error, which becomes `inconclusive` with reason `unsupported` or `verifier_error`, never an empty list read as zero. Core holds only `Measurement`, criterion state and the comparison; metric names like `coverage` or `p95_latency_ms` live in packs.

**Rests on.** Section 1: Flagger's `MetricTemplate` returning one float64 and Argo's provider plus condition split (https://docs.flagger.app/usage/metrics). Section 2, Keptn: each objective pairs an `analysisValueTemplateRef` (the query) with a `target` of `failure` and `warning` conditions, and the analysis returns a status per objective (https://keptn.sh/stable/docs/reference/crd-reference/analysisdefinition/, https://keptn.sh/stable/docs/guides/slo/). Section 3, Codecov: `codecov/project` and `codecov/patch` each post their own status from their own `target` and `threshold` (https://docs.codecov.com/docs/commit-status). Section 3, SonarQube: each condition is a metric, an operator and an error value, judged one by one, and a pull request showed coverage as "–" while its gate passed (https://docs.sonarsource.com/sonarqube-server/quality-standards-administration/managing-quality-gates/introduction-to-quality-gates, https://community.sonarsource.com/t/quality-gates-passes-without-showing-code-coverage-for-some-of-the-pull-requests/70588). Section 4: Inspect's typed `Score` with a `reason` (https://inspect.aisi.org.uk/scorers.html). Code reading facts 1, 2 and 5.

**Conflicts.** Changes `ActionResult` and `Criterion` in core and the pack manifest of ADR 028, so **ADR 029 is needed**. Consistent with ADRs 022, 026 and rules 9 and 10.

**Checked in the second pass.** Section 2's Keptn objectives and section 3's SonarQube conditions both keep the metric source (a query, a metric) apart from the comparison (a target, an operator and an error value), and both report a result per objective or condition. That matches D3's split, in which the verifier emits named measurements and core compares them, with a state per criterion. Section 3's Codecov posts one status per check from that check's own target, which matches one state per criterion and not one per verifier. SonarQube's "–" next to a passed gate is the case D3's rule 10 clause covers: a missing value becomes `inconclusive`, never an empty list read as zero.

### D4 Baselines, relative targets, windows, repeated runs and aggregation

**Decision.** A measured criterion is `metric op target` with `op` in `<, <=, >, >=, ==`, a `unit` that must equal the declared unit, and optionally:
- `baseline: at_start` (measured once when the objective starts and frozen, recorded in the audit log) or a fixed number, with `change` as an absolute or percentage delta against it ("coverage of ./internal/feature not lower than at start", "p95 not more than 10% above baseline");
- `samples: N` with a reducer (`all`, `k_of_n`, `median`, `p95`, `max`, `min`, `mean`) and a `min_samples` below which the state is `inconclusive: too_few_samples`.

Default for a noisy signal is `median` over N with `min_samples`; for a pass/fail signal it is `all`, never "any rerun passes". A statistical canary judge (Kayenta's Mann-Whitney) is out of scope for Phase 41; `window` over wall-clock time is dropped from the loop and belongs to D5, together with error budgets and burn rate.

**No baseline is `inconclusive: no_baseline`.** A relative target whose baseline is absent resolves to `inconclusive` with reason `no_baseline`, not to `not_met`. The baseline is absent when the `at_start` measurement was itself inconclusive or never ran. Under D1 the criterion then blocks completion without counting as a failed pass. The baseline is never approximated from another commit or a later measurement. It stays absent for the life of the objective until a person sets one through the API, which is audited (D7). The person sees the baseline value beside the target, because a baseline taken from a start that was already bad is met by construction.

**Rests on.** Section 1: Argo's `count`/`failureLimit`/`consecutiveSuccessLimit`, Kayenta's contemporaneous baseline. Section 2, SRE workbook: SLOs over rolling windows of whole weeks, the error budget as 100% minus the SLO, multiwindow burn-rate alerting, and the warning that an SLO set from current performance is met by construction (https://sre.google/workbook/implementing-slos/, https://sre.google/workbook/alerting-on-slos/). Section 2, OpenSLO: the spec pages holding `timeWindow` and `budgetingMethod` were not read, so nothing here rests on them (https://openslo.com/). Section 2, Keptn: the current Analysis compares only with fixed thresholds or ranges, and v1's comparison with previous evaluations was not read (https://keptn.sh/stable/docs/reference/crd-reference/analysisdefinition/). Section 3, Codecov: `target: auto` compares with a base that moves with the base branch, is approximated by pseudo-comparison when the base has no report, and turns into an error in the UI with `allow_pseudo_compare: False`. Users hit "Missing base commit" in practice (https://docs.codecov.com/docs/comparing-commits, https://github.com/codecov/feedback/issues/861). Section 3, SonarQube: new code is a relative target with no stored number, and the fudge factor turns too few lines into a pass. Section 4: Inspect's epochs and reducers, `pass_at` versus `pass_k`. Section 7: Luo et al., F.12, rerun-until-green hides real bugs (https://mir.cs.illinois.edu/lamyaa/publications/fse14.pdf).

**Conflicts.** None. A frozen `at_start` baseline is a target the loop cannot edit (D7).

**Changed in the second pass.** D4 said nothing about a relative target with no baseline. It now resolves to `inconclusive: no_baseline`, which is consistent with D1's rule that an absent measurement is never `not_met`, and D1's reason list gains `no_baseline` to match. The baseline is never approximated, and the person sees its value. This comes from section 3's Codecov subsection: a moving, approximated base that users report as "Missing base commit", with no documented status when no base exists (Codecov takeaway 2). It also comes from section 2's SRE workbook subsection, where a target taken from past performance is met by construction (takeaway 4). The SRE workbook's windows, error budget and burn rate, together with the OpenSLO and Keptn subsections of section 2, confirm that wall-clock windows belong to D5 rather than the loop, and they changed nothing else in D4.

### D5 Sustain for standing objectives, and reconcile

**Decision.** The loop evaluates criteria once per run and converges (rule 8). `sustain` is read by reconcile, not by the loop. It is a budget over a rolling window, not a streak: `sustain: {window: 28d, budget: 0}` reads "no pass in the last four weeks ended `not_met`", and `budget: 0.1` allows one such pass in ten. Reconcile records each pass's criterion states with the time of the pass, and a criterion is sustained while the share of its passes in the window that ended `not_met` stays within the budget. The window is rolling, never calendar. A pass that ended `inconclusive` is left out of both counts, does not spend budget and is reported apart. When the window holds fewer settled passes than `sustain.min_passes`, the sustain state is `inconclusive: too_few_samples`, not healthy, because with three passes in a window one failure is a third of them. The latest pass's state is shown beside the budget left, so a person can see a criterion that has recovered after spending budget. Burn-rate alerting is not adopted in Phase 41; the breaker stays the alert. This is per criterion, beside the existing `ScoreStreak` (`reconcile/run.go:508-518`), not a replacement for it. Only `not_met` on a required criterion counts towards `BreakerFailures`; `inconclusive` does not. That directly addresses fact 4: a stream pass whose deterministic criteria are met, such as a PR opened at a green head, is not a failed pass because a model judged a prose criterion unmet. Sustain compares each pass with its target, never with earlier passes' values; a relative target uses D4's frozen baseline. Drift from the converged fingerprint (`sense.go:34,77`) stays the trigger for re-running; a criterion state change is not a second drift signal.

**Rests on.** Section 1: Argo's `consecutiveSuccessLimit` and `interval`, the streak form this replaces. Section 2, SRE workbook: the error budget as 100% minus the SLO over a window, rolling windows of whole weeks preferred to calendar ones for tracking experience, multiwindow burn-rate alerting with a short window that lets an alert stop once the burn has stopped, and too few events named as the noisy case (https://sre.google/workbook/implementing-slos/, https://sre.google/workbook/alerting-on-slos/); Pyrra's "Too few requests!" warning (https://github.com/pyrra-dev/pyrra/issues/1925). Section 2, OpenSLO: `timeWindow` and `budgetingMethod` were not read, so nothing here rests on them (https://openslo.com/). Section 2, Keptn: the current Analysis compares only with fixed thresholds or ranges, and v1's comparison with previous evaluations was not read (https://keptn.sh/stable/docs/reference/crd-reference/analysisdefinition/). Section 7, takeaways 1 and 4. Code reading facts 4 and 5.

**Conflicts.** None with rule 8 or ADR 015; it puts time in reconcile on purpose. It changes the breaker's input and adds `sustain.window`, `sustain.budget` and `sustain.min_passes` to the criterion, which ADR 029 must state.

**Changed in the second pass.** Sustain was N consecutive `met` passes; it is now a budget of `not_met` passes over a rolling window, with `min_passes` and `inconclusive: too_few_samples` for a thin window. Section 2's SRE workbook subsection drove it. Its error budget makes success over time a spendable quantity over a window (takeaway 1). A streak is only the long-window half of its alerting, so a recovered criterion stays broken until N more passes (takeaway 2). It names too few events as the noisy case (takeaway 3), and it prefers rolling windows to calendar ones. Section 2's OpenSLO subsection did not get past the landing page, so the rolling-window choice rests on the workbook alone. Section 2's Keptn subsection has no comparison with previous evaluations on the pages read, so sustain adds none.

### D6 How criteria are given, validated and shown

**Decision.**
- **API.** The create request (`handler/objective.go:25-34`) gains an optional `success_criteria` array with the D1 to D4 fields. Template criteria remain the default; request criteria are added to them, and a request criterion with the same `id` as a template criterion may tighten it (a stricter target, `required: true`) but not loosen or remove it. Since `docs/openapi.yaml` does not exist (fact 3), the phase must either create the spec or correct rule 6.
- **Prose and data.** Every criterion has a `description` a person writes. A `measured` or `verified` criterion also carries data: the verifier ID and the D3 and D4 fields. The binding between the two is that explicit ID, never matched from the prose the way Gherkin binds a step to its definition by text. A `judged` criterion's description names an observable outcome ("an open PR with tests"), not an activity ("review the code", "help", "analyze"), and its `evidence` field names what the judge will look at. One criterion holds one observable outcome. The count is not capped: the OKR guide's "around three key results per objective" is advice, not a rule.
- **CLI.** `krk objective create --criteria-file criteria.yaml` is the primary form (YAML, the same shape as the API). A repeatable `--criterion` flag takes `key=value` pairs separated by `;` for one-off cases only. The help and the example file show one observable outcome per criterion and a judged criterion with its `evidence`. `krk verifier list` shows each verifier's declared metrics, units and parameters; `krk objective criteria <id>` shows per criterion its kind, target, last measured values with unit and source, state and reason.
- **Validation at create time.** Reject an unknown verifier, a metric the verifier does not declare, a unit mismatch, an unknown parameter, an `op` without a target, a reserved (third-party) verifier, a `judged` criterion with no `evidence`, and an objective with no required criterion. Errors name the field. The check cannot tell an outcome from an activity; the help text carries that rule.
- **What a person sees.** Per criterion: met, not met or inconclusive with its reason, the number against the target and baseline, and whether a model or code decided it. A criterion whose verifier did not run shows `inconclusive: not_run`, never met. A `required: false` criterion with a weight is shown as progress (for example 0.7 of 1.0), apart from the gate, so an expected partial score does not read as failure. The web objective page shows the same.

**Rests on.** Section 1 (Argo and Flagger declare criteria as data in the same object as the rollout). Section 2, OpenSLO: the README keeps "platform-specific implementation details" out of the spec, the same split as a criterion declaration and the verifier that settles it (https://raw.githubusercontent.com/OpenSLO/OpenSLO/main/README.md). ### D7 Safety and anti-gaming

**Decision.**
- Targets, baselines, reducers, sample counts and sustain budgets are fixed at create time and stored with the objective. The loop has no capability that writes them; a change goes through the API by a person, is audited, and restarts the criterion's sustain window (D5).
- A verifier is a pack capability. A discovered MCP tool can never be a verifier (extends verify.go:88 and ADR 022 from "never met" to "rejected at create time").
- A `measured` or `verified` criterion is never handed to the model: when its verifier did not run, the state is `inconclusive: not_run`, not a judgement. This removes the verify.go:106 fallback for criteria that name a verifier.
- **Unreported or skipped is `not_run`, whatever the cause.** A verifier that reports skipped or neutral, and one that has not reported when the verify step's bounded wait ends, both give `inconclusive: not_run`. Neither is ever `met`, as GitHub's `if`-skipped job is, and neither is left pending with no end, as its path-skipped workflow is. Neither is `not_met` either: under D1 the criterion blocks completion, does not count towards the breaker, and is reported apart. A run that stopped at its iteration limit has ended but not succeeded, and that run outcome settles no criterion. The verifiers settle them from the world the run left, and one that did not report there is `not_run`.
- **Only the named verifier, only this commit.** A criterion is settled only by a measurement from the verifier it names, taken at the commit being judged. A measurement from any other capability or from an earlier commit is audited but settles nothing. If no measurement qualifies, the state is `not_run`.
- Every measurement is audited with its verifier, parameters, value, unit, source, trust and the commit it was taken at.
- Anti-gaming: when a pass changes the files a criterion's verifier reads its definition from (the test files behind `tests-pass`, the coverage config, the benchmark, the metric query), the criterion is `inconclusive: measure_changed` and needs a person, like SWE-bench running the original FAIL_TO_PASS/PASS_TO_PASS tests rather than the patch's. Packs declare those paths with the verifier.

**Rests on.** Section 3, GitHub required status checks: `skipped` counts as passing, a path-skipped workflow stays "Pending" and blocks forever, an `if`-skipped job "reports "Success"", the expected app pins who may set a check, and "Checks from earlier commits don't satisfy the requirement" (https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches, https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/troubleshooting-required-status-checks). Section 4: SWE-bench's fixed test lists, Inspect's scorer kept apart from the solver. Section 5: LangGraph routes a run that ran out of steps to the same `END` as one that finished, and AutoGen joins budget stops and approvals with OR, telling them apart only by a free-text `stop_reason` (https://docs.langchain.com/oss/python/langgraph/graph-api, https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/termination.html). AutoGen #6826: a stop word in the task ended the run (https://github.com/microsoft/autogen/issues/6826). Section 6, Gherkin: an undefined step skipped and then counted as passed (https://github.com/cucumber/cucumber-jvm/issues/1946). Section 7: Luo et al. F.12. Code reading fact 1 (reserved verifiers, the judge fallback).

**Conflicts.** None; it reinforces ADR 022 and rule 9. Removing the judge fallback for verifier-named criteria changes `software.objective.delivery` behaviour on docs-only tasks (fact 4), which is wanted: the template should use the D8 deterministic booleans or not name the verifier.

**Changed in the second pass.** A skipped or unreported verifier now resolves to `inconclusive: not_run`, a distinct state that is neither `met` nor `not_met`, after a bounded wait. A criterion is settled only by its named verifier at the commit being judged. That agrees with D1 as it now stands: `inconclusive` blocks completion without feeding the breaker, and a run outcome such as a spent budget settles no criterion. D1's reason list gains `measure_changed`, which this decision already used. Section 3's GitHub subsection drove the change. GitHub has two opposite answers for "did not run" (takeaway 1), and waiting forever needs a bound (takeaway 2). The expected app and the latest commit are its source and commit pins (takeaways 3 and 4). Section 5 (LangGraph takeaway 1, AutoGen takeaways 1 and 2) supplied the rule that a run stopped at its limit has ended but not succeeded. The restarted sustain window follows D5.
